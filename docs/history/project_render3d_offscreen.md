M21 (Phase 2 of the engine-expansion plan — see [[project-ui-gpu-backend]] for M20, the prior phase) builds the one shared primitive that both `ui::Viewport3D` (M22) and widget shader effects (M24) need: rendering a `render3d::Object3D` scene into an off-screen texture (not the window swapchain) and reading the pixels back to the CPU, plus the reverse direction (CPU pixels → GPU texture). Reason it's needed: `sdl3::Renderer` (2D, all of `ui::`) and `render3d::Canvas`/`sdl3::GpuDevice` (SDL_GPU) are two separate SDL subsystems with no documented interop in this environment — CPU readback/upload is the only mechanism available, and this codebase already uses exactly that mechanism for its Radiance HDR loader and its shadow-map/IBL-cubemap render-to-texture code (M7-M13 of the prior render3d phase), so M21 is a continuation of an established pattern, not a new one.

## M21 done — `lib/include/render3d/offscreen.hpp`

- **`OffscreenTarget`**: owns a color (`COLOR_TARGET|SAMPLER`) + depth (`DEPTH_STENCIL_TARGET`) `GpuTexture` pair, lazily (re)created via `EnsureSize(device, w, h, colorFormat, depthFormat)` only when the requested size/format actually changes — mirrors `Canvas::RecreateDepthTexture`'s exact pattern (`canvas.hpp:133-149`), duplicated for the color texture.
- **`Canvas::RenderObjectOffscreen(Object3D&, const Camera&, OffscreenTarget&)`** (new `Canvas` member, declared in `canvas.hpp` via a forward-declared `OffscreenTarget` — avoids a circular include since `offscreen.hpp` needs `Canvas`'s full definition — body lives in `offscreen.hpp`): reuses the REAL per-node `OnDraw()` dispatch (same one `Canvas::DrawObject` uses) by saving/clearing/restoring `Canvas::m_drawList` and temporarily forcing `m_frameActive=true` around the traverse — `DrawMesh`/`DrawMeshGroup` only push onto `m_drawList` when `m_frameActive` is true, so this trick lets `Shape::OnDraw` (and any future `Object3D` subclass's `OnDraw`) work completely unmodified outside a normal `Begin()`/`End()` frame. Uses its own LOCAL `sdl3::GpuCommandBuffer` (via `m_device.AcquireCommandBuffer()`), entirely independent of `m_commandBuffer` — safe to call whether or not a window frame is currently open.
- **Deliberate scope cut, matching an existing precedent**: no shadows, no IBL. `InstancedMesh`/`SkinnedMesh` (M16/M17 of the prior render3d phase) already don't get shadows/IBL either — same documented cut, not an oversight. This let the implementation skip `canvas.hpp`'s ~250-line shadow pre-pass and skybox/IBL-sampler-binding code entirely and mirror only the "plain" (`hasShadows=false && hasEnvironment=false`) branch of `Canvas::End()`'s main draw loop — including its exact `PipelineKey` construction and the `needsBuiltShader` branch (precompiled-Phong 32-byte `MaterialUBO` vs. `ShaderBuilder`-generated 48-byte one with `emissive`/`useIBL`) documented in `memory/project_render3d_threejs_port.md`'s Phase 2 notes — getting this exactly right (not guessed) was the main risk in this milestone, resolved by reading `Canvas::End()` directly rather than reconstructing the UBO layouts from memory.
- **`RenderObjectToTexture(Canvas&, Object3D&, Camera, OffscreenTarget&, std::vector<uint8_t>&)`** (free function): overwrites `camera.aspect` from `target.Width()/target.Height()` before drawing — this is the exact mechanism that will later let a `Viewport3D` widget of any box shape avoid distorting the 3D projection (M22), regardless of the caller also having set `camera.aspect` themselves (defensive double-write). Calls `RenderObjectOffscreen`, then downloads the color texture via a **separate** command buffer + `GpuTransferBuffer` (`gpu.hpp`'s `DOWNLOAD` usage) + `GpuCopyPass::DownloadFromTexture` — with an explicit `m_device.WaitIdle()` after both the render submit and the download submit, since SDL_GPU gives no ordering guarantee between two independent command buffers without explicit synchronization (same caution already established in this repo's own pixel-readback tests, e.g. `tests/shadow_smoke_test.cpp`).
- **`UploadSurfaceToGpuTexture(GpuDevice&, pixels, w, h, format)`** (free function, reverse direction): CPU buffer → `GpuTransferBuffer` (`UPLOAD` usage) → `GpuTexture` via `GpuCopyPass::UploadToTexture`. Not consumed by M21 itself (no caller yet) — built and independently tested now because M23/M24 (widget shader effects) need it, and it's cheap to verify in isolation today rather than re-deriving the pattern later.

## Real bug found and fixed (unrelated to this milestone's own code, but blocked verifying it)

`lib/include/sdl3/render.hpp`'s `Renderer::DrawPoints`/`DrawLines` each had **3 overloads where 2 had become byte-identical signatures** (`std::span<const FPoint> pts` declared twice) — a genuine `-Werror` compile error blocking anything that includes `render.hpp` (which `offscreen.hpp` does transitively via `gpu.hpp`), discovered while trying to build `offscreen_smoke_test`. Root cause: a prior, apparently-incomplete pass had changed the middle overload's parameter from `std::span<const SDL_FPoint>` to `std::span<const FPoint>` (using a direct `(SDL_FPoint*)` reinterpret-cast on `pts.data()` — valid since `FPoint{float x,y}` and `SDL_FPoint{float x,y}` are layout-identical, `structs.hpp:827-833`) but left behind a THIRD overload (`std::span<const FPoint>` too, copying into a `std::vector<FPoint>` and recursing) that existed specifically to convert into the OLD `SDL_FPoint`-typed overload — now dead code with a colliding signature. **Not caused by this session's own edits** (confirmed via `git diff`/coordination with a concurrent peer Claude Code session also working in this repo, `sdl3-wrapper-35` — see cross-session message log). Fixed by deleting the now-redundant third overload in both `DrawPoints` and `DrawLines` (the direct-reinterpret-cast overload already does the job) — a pure dead-code removal, not a behavior change. Confirmed no other `std::span<const FPoint>`/`std::span<const SDL_FPoint>` pairs in `render.hpp` have the same collision (checked every `std::span<const F{Point,Rect}>`-parametrized method).
