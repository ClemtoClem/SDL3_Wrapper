## Design history — Style Engine v2 (why it looks the way it does)

1. First attempt (Phase 0 plan) explicitly said "no CSS system, stay on UiTheme+WidgetColors, StyleSystem
   stays unwired — out of scope." User rejected this when asked to add glass/gloss rendering: wanted the
   effect built through `styles.hpp` via static `UiStyle` factory functions instead of a bespoke
   `UiGlass` component.
2. That led to reviving `StyleSystem`/`UiStyleSheet` for real (they existed in the codebase but were never
   called by anything — confirmed via repo-wide grep before this session). Extended `StyleProp`
   enum + fixed-field `UiStyle`/`UiComputedStyle` structs with `Gloss`/`Glow`/`GlowColor`, wired
   `RenderSystem` to consult `ResolvedStyle` for `UiPanel`/`UiButton` backgrounds.
3. User then asked for something much bigger: ALL widget aesthetics driven by style, widget structs
   stripped of fontSize/color/border fields entirely, CSS-like inheritance, and a "priority flag" system
   (inherit-from-parent / inherit-from-root / private / heritable, with a value possibly split into a
   private value vs. a value exported to children). I proposed a concrete flag-based design via
   AskUserQuestion — **user rejected the flags model** in favor of something closer to real CSS: named
   style classes with an explicit priority order (order in the class list = priority, last wins), a
   universal `"root"` fallback class every widget implicitly carries, and a dynamic string-keyed API:
   `gui.createStyleClass(name, style)` / `gui.setStyleProperty("target.property", value)`.
4. User then pointed at a concrete reference implementation on disk:
   `/home/clement/Documents/Programs/Programs_C/SDL/Video_Projects/SDL3_ui/src/UI/Style.hpp` (a sibling
   project, NOT part of this repo) — "adapt this for the ECS architecture." That file uses a
   type-erased property bag (`std::unordered_map<std::type_index, {std::any value, name}>`) with tiny
   per-property structs generated by macros (`PROPERTY_COLOR(BackgroundColor, "background-color")`, ...)
   instead of a fixed-field struct + enum mask. This is the design that shipped — see
   `src/ui/styles.hpp`'s own header comment for the final shape. Scope was deliberately narrowed to
   **visual-only** properties (color/font-size/border/radius/padding/gap/opacity/gloss/glow) — structural
   and behavioral widget data (checked, value, min/max, callbacks, text content) stays on ECS components
   exactly as before; that split is the ECS-idiomatic adaptation of a reference design that in the
   original project also stuffed behavioral properties into the same bag.

**Why this matters for future work:** if the user asks to add a NEW style property, the pattern is one
`UI_PROP_COLOR/FLOAT/SIDES/CORNERS/ALIGN(Name, "css-name")` macro line in `styles.hpp`'s `prop::`
namespace, a fluent setter one-liner on `UiStyle`, a named accessor pair on `ResolvedStyle`, and an entry
in the relevant `detail::*PropRegistry()` table if it should be reachable via `setStyleProperty`. No enum,
no `StyleMask`, no `MERGE_*` macro block — that machinery was deleted.

5. Later in the same session, border width/radius were pushed further: the user explicitly required
   ("obligatoirement") that both be full `Sides`/`Corners` (not a single float) so every edge/corner is
   independently configurable — `prop::BordersWidth` is `Sides`-typed (`setBordersWidth(Sides)` +
   `setBordersWidth(float)` convenience overload, mirroring the pre-existing `Padding`/`Margin` pattern),
   `prop::BordersRadius` is `Corners`-typed (new `UI_PROP_CORNERS` macro added specifically for this —
   `math::Corners`/`math::Corners` alias in components.hpp already existed and slots directly into
   `Renderer::fillRoundedRect`/`drawRoundedRect`, so no conversion helper was needed for the RADIUS path).
   `ResolvedStyle::bordersWidth(Sides fallback)`/`bordersRadius(Corners fallback)` replaced the old
   float-returning `borderWidth`/`borderRadius`. **Known scope limit**: `RenderSystem`'s border-drawing
   (the concentric-outline loop in the `UiPanel`/`UiButton` blocks in systems.hpp) fully honors per-corner
   `BordersRadius` (each concentric ring insets `tl/tr/bl/br` independently), but the outline-count loop
   still uses a single representative value (`borderWidth.top`) for thickness — genuinely different
   per-edge border WIDTHS are stored/resolved correctly but not yet rendered differently per edge. If a
   future phase needs that (e.g. a title bar with only a bottom border), either extend that loop to draw
   4 separate edges, or switch to `sdl3::Renderer::drawRoundedBorderedRect(rect, Sides border, Corners c)`
   (render.hpp) which already draws a true per-side annulus border in one call — it wasn't used here to
   avoid changing the visual bounds (it draws the border OUTSET beyond `rect`, whereas the current
   concentric loop draws INSET within it).

## Bug found and fixed (real, not hypothetical)

`StyleSystem::resolve()` (styles.hpp) had a pre-existing bug inherited from the original (dead) code:
its second pass did `world.Query<UiStyleDirty>([&](Entity e, UiStyleDirty&){ world.remove_component<UiStyleDirty>(e); })`
— removing a component INSIDE the query that iterates that same component triggers an archetype
migration mid-iteration, corrupting the iterator. This never fired before because nothing ever called
`StyleSystem::resolve()` (confirmed dead code before this session). The moment it was wired into
`Ui::render()`, `ui_minimal` segfaulted immediately. Fixed by collecting dirty entities into a
`std::vector<Entity>` first, then removing the component in a second, non-iterating loop. **Lesson for
this codebase**: any `ArchetypeRegistry::Query<T>` callback that calls `remove_component<T>`/`add_component`
on the same T inside the loop needs the same collect-then-mutate treatment — grep for this pattern if
extending InputSystem/RenderSystem loops in later phases.

## Phase 1 — Popup/Modal overlay system (done)

Implemented exactly per the plan's decision #1, no deviations:
- `UiOverlayLayer{int order=0}` + `UiPopupState{bool open, modal; Entity trigger}` (components.hpp),
  `isDescendantOrSelf(world, e, ancestor)` helper next to `isHiddenRecursive`/`isDisabledRecursive`.
- `RenderSystem::run()`'s Fixed-pass now collects `(order, Entity)` pairs and `std::stable_sort`s before
  drawing (was: raw query iteration order) — `#include <algorithm>` added to systems.hpp for this.
- `InputSystem` gained `modalStack` (private) + public `openModal/closeModal/hasOpenModal`. `Frame`
  gained `bool escape`; `handleEvent` now recognizes `SDLK_ESCAPE`. `dispatch()`: Escape pops+closes the
  top modal and returns early; both `hitOk` lambdas (in `tick()` for tooltips and in `dispatch()`) gate on
  `modalStack` via `isDescendantOrSelf`; a new block before the ComboBox handling collects
  (then closes, in a second pass — same collect-then-mutate pattern as the StyleSystem fix above) any
  open non-modal popup whose screen rect AND trigger's screen rect are both outside the click point.
- Free functions `ui::openPopup`/`closePopup` (systems.hpp, take `LayoutSystem&` — modal variants are
  `InputSystem` methods instead since they touch the private stack, a deliberate small deviation from the
  plan's "4 free functions" phrasing, noted then accepted implicitly by proceeding).
- `UiFactory::popup()` (Fixed+hidden+UiPopupState, themed like a panel) and `UiFactory::modal(WidgetBuilder
  content)` (wraps content with a full-screen absolute-positioned scrim child + centers content via
  `.absolute().anchor(Center)`) in factory.hpp. `WidgetBuilder::overlayOrder(int)` setter added for future
  nested-popup use (Phase 5 submenus).
- `Ui` facade (ui.hpp) got passthroughs: `openPopup/closePopup/openModal/closeModal/hasOpenModal`.
- **Not yet exercised by an automated test** — `ui_smoke_test_6` (popup/modal/selection/resize coverage)
  is deferred to Phase 10 per the plan's own Verification section, alongside Phase 2's primitives. Only
  verified so far via clean compile + the existing (unrelated) regression suite staying green.
- **For Phase 10 example apps**: existing examples' main loops treat Escape as "quit the whole app"
  BEFORE forwarding the event to `ui::`/`InputSystem` — new Aero examples should check
  `gui.hasOpenModal()` first and only quit-on-Escape when no modal is open (dismissing the modal
  otherwise), or Escape will never reach `InputSystem::dispatch()`'s modal-close logic at all.

## Phase 2 — interaction.hpp shared primitives (done)

New file `src/ui/interaction.hpp`, included by `components.hpp`-adjacent headers `systems.hpp`,
`factory.hpp`, `ui.hpp` (right after `glyphs.hpp`, before `styles.hpp`/`scene.hpp`):
- `SelectionState{unordered_set<int> selected; int anchor,lastClicked;}` + `UiSelection{SelectionState
  state; bool multiSelect=true;}` + free function `applySelectionClick(state, index, ctrl, shift,
  multiSelect=true)` — Explorer/Finder-style click semantics (plain=replace, ctrl=toggle,
  shift=range-from-anchor). Pure, no ECS access — Table (Phase 6)/TreeNode+Selectable (Phase 4) will
  attach `UiSelection` and call this from their own hit-test.
- `UiResizeHandle{Orientation orient; function<float()> getBefore/getAfter; function<void(float)>
  setBefore/setAfter; float minBefore/maxBefore/minAfter/maxAfter; bool dragging,hovered; float
  dragStartMouse/Before/After;}` + free function `resolveResizeDrag(m_handle, mouseCoord)` — generic 1D
  drag-to-resize, will back Splitter (Phase 8) and Table column resize (Phase 6).
- `InputSystem::dispatch()` (systems.hpp) already wired the drag lifecycle for `UiResizeHandle` this
  phase (not deferred to Phase 6/8): new private member `Entity resizeDrag{}`, and a new block placed
  right after the existing auto-scrollbar drag block — press-latches onto a hit `UiResizeHandle` entity,
  drag calls `resolveResizeDrag` + `layout.markDirty()` each frame held, release un-latches. Phase 6/8
  widgets only need to attach the component + accessors; no per-widget drag loop duplication needed.
- **Not yet exercised by an automated test** — same as Phase 1, `ui_smoke_test_6` (deferred to Phase 10)
  is the first place these get direct coverage. Verified so far via clean compile + full regression
  suite (5 smoke tests + both examples headless) staying green.
