`render3d::` (`lib/include/render3d/`) is a 3D rendering layer on `sdl3::Gpu*`, built in two phases, both complete and GPU-verified (not just syntax-checked) as of 2026-08-21.

## Phase 1 (foundation)
`math::{FVector2/3/4, FMatrix4, FQuaternion, FAABB, FPlane, FRay, FFrustum}` (math.hpp) + `render3d::{Vertex3D, Mesh (Cube/Sphere/Plane), Material, DirectionalLight/AmbientLight, Camera, ShaderProgram, Canvas}`. Canvas is immediate-mode: `Begin()/DrawMesh()/End()` against two **precompiled** shaders (`mesh_basic`/`mesh_phong`, built offline via `assets/shaders/compiler.sh`).

Real bug fixed: winding/front-face convention. All procedural geometry is authored CCW-when-viewed-from-outside; the pipeline uses `front_face = CLOCKWISE` (not COUNTER_CLOCKWISE) to compensate `FMatrix4::Perspective()`'s Y-flip for Vulkan clip space — this was backwards originally, causing inverted-looking cube faces. **Why it matters:** any new geometry generator must be checked against this convention, not assumed.

## Phase 2 — three.js port (scene graph, geometries, lights, PBR, shader builder)
Full plan/history: `/home/clement/.claude/plans/optimized-humming-toast.md` (6 milestones M0–M6, all done). Key additions:

- **Runtime GLSL shader compiler** (`shader_compiler.hpp`): `shaderc` (GLSL→SPIR-V) + `spirv-cross` (SPIR-V→MSL), both pre-installed system-wide via apt (`libshaderc-dev`, `libspirv-cross-c-shared-dev`). Makefile links `-lshaderc -lspirv-cross-{msl,glsl,core,util}`.
- **Chunk-based shader DSL** (`shader_chunks.hpp` + `shader_builder.hpp`): `ShaderBuilder` fluent API (`.Color().Texture().Lit().PointLights(n).SpotLights(n).Shadow(n)...`), composes GLSL chunks in C++ (not a `#include`-resolver like three.js). `.Shadow(n)` is accepted/stored but is an **inert stub** — always unshadowed (factor=1.0); real shadow mapping is out of scope.
- **Object3D scene graph** (`object3d.hpp`): real parent/child hierarchy, `std::vector<std::unique_ptr<Object3D>>` owned children, raw non-owning `parent`. Both copy AND move are `= delete`d (move would dangle children's parent pointers). World/local matrices recomputed every call, no dirty-flag caching — deliberate simplification to avoid stale-cache bugs.
- **Shape** (`shape.hpp`): `Object3D` subclass owning `Mesh` + per-face `Material` vector via `Mesh::Group{start,count,materialIndex}`.
- **Full geometry suite** (`mesh.hpp`): quadrics (Cylinder/Cone/Torus/Circle/Ring), polyhedra (Tetrahedron/Octahedron/Icosahedron/Dodecahedron via `Polyhedron()` subdivide+project), curve-based (Lathe/Tube/TorusKnot/Extrude) needing new `shape2d.hpp` (ear-clip triangulation with holes) and `curve.hpp` (Curve3, Frenet frames via parallel transport).
- **PointLight/SpotLight** (`light.hpp`): real shader lighting terms, not inert structs. Fixed bindings: PointLightUBO at set=3/binding=2, SpotLightUBO at set=3/binding=3 — **bindings are NOT contiguous by design**; SDL_GPU push slot must match the literal GLSL binding number, so SpotLight stays at slot 3 even when no point lights are present (a real bug caught: slot was initially `m_pointLights.empty() ? 2 : 3`).
- **PBR metallic-roughness material** (`Material::Pbr()`): full Cook-Torrance GGX BRDF in `shader_chunks::LIGHTING_FUNC_PBR`, verified pixel-exact against a hand-computed BRDF value in `tests/shader_builder_smoke_test.cpp`. No IBL/environment maps (explicit scope cut).
- **Two divergent `MaterialUBO` layouts** in `canvas.hpp::End()`: old 32-byte precompiled-Phong shape vs new 48-byte ShaderBuilder shape (adds emissive). The branch picking which one to push MUST exactly match `needsBuiltShader = key.shader==PBR || key.pointLightCount>0 || key.spotLightCount>0` in `GetOrCreatePipeline` — a real bug was initially only checking light counts, silently mismatching the UBO for PBR-with-zero-lights draws. **If touching canvas.hpp's uniform-push logic, keep these two conditions in sync.**

## Explicitly out of scope (deliberate, not oversight)
Real shadow mapping, IBL/environment maps, `Points`/`Line`/`Sprite`/`InstancedMesh`/`SkinnedMesh`/`LOD` (future `Object3D` subclasses), `EdgesGeometry`/`WireframeGeometry`/`CapsuleGeometry`, full texture-asset pipeline (only a minimal `LoadTextureFromFile` helper exists in `texture_loader.hpp`).

## Verification approach (reusable technique)
Screenshot tooling (`xwd`) was broken all session (X server `BadMatch` on `X_GetImage`, environment-level, not code-related — no alternative tool available either). Verification instead relied on:
- CPU-only geometric invariants: `ExpectConsistentWinding` (cross product · averaged normal > 0) and `ExpectWatertightManifold` (every position-keyed edge shared by exactly 2 triangles) in `tests/render3d_smoke_test.cpp` — caught 4 real winding bugs (Sphere, Ring, Lathe, Extrude side walls) with zero rendering needed.
- GPU pixel-readback compared to hand-computed shading values (exact byte match ± tolerance) for both Unlit and PBR paths.
**Why it matters:** this was arguably more rigorous than screenshots would have been — prefer this technique over visual-only checks even once screenshot tooling is fixed.

## Phase 3 (shadow mapping, IBL, remaining Object3D subclasses) — IN PROGRESS
Full plan: `/home/clement/.claude/plans/optimized-humming-toast.md` (M7 onward, continuing the M0–M6 numbering above). Started 2026-08-22.

**Critical hard constraint discovered in M8 (load-bearing for all remaining milestones)**: SDL_GPU caps **fragment uniform buffers at exactly 4 slots per stage** (`slot_index exceeds MAX_UNIFORM_BUFFERS_PER_STAGE` at runtime, not compile time — only surfaces when you actually try to push slot 4+). Phase 2 already used all 4 (0=Material, 1=Light, 2=PointLightArray, 3=SpotLightArray). **There is no slot 5.** Any new scene-level fragment data (shadow matrices in M8, and whatever IBL params M14 needs) must be *folded into one of the existing 4 UBOs*, not added as a new binding — M8 solved this by merging `ShadowMatrixUBO` directly into `LightUBO` itself (`shader_chunks::LIGHT_UBO_SHADOW` replaces `LIGHT_UBO_BASE` at the *same* binding=1 when shadows are enabled; mirrored on the C++ side as `LightUBOWithShadow` in `canvas.hpp::End()`, `base` field embedding the plain `LightUBO` struct followed by the shadow fields — std140/C++ layout happen to agree here since `LightUBO` is exactly 64 bytes, already 16-byte aligned, so no manual padding was needed). **When touching M9 (point-shadow cubemap) or M14 (IBL), check this budget again before adding anything** — samplers (`set=2`) are comparatively roomy (4 already bound with room to spare) but fragment UBOs are maxed out.

**Full confirmed per-stage limits** (from SDL3 source, `SDL/src/gpu/SDL_sysgpu.h`, not documented in the public header — grep it directly if in doubt rather than guessing): `MAX_TEXTURE_SAMPLERS_PER_STAGE=16`, `MAX_STORAGE_TEXTURES_PER_STAGE=8`, `MAX_STORAGE_BUFFERS_PER_STAGE=8`, `MAX_UNIFORM_BUFFERS_PER_STAGE=4`. So: fragment UBOs are the tight one (4/4 used already); samplers have headroom (4/16 used, M9's point-shadow cubemap + M14's 3 IBL textures still leaves room); storage buffers (8/8 free) are what M17's SkinnedMesh bone-matrix palette should use instead of a UBO, since UBO slots are gone.

**M7 done**: light-space matrix builders (`DirectionalLight`/`SpotLight`/`PointLight::ShadowViewProjection()` in `light.hpp`, each light struct gained `castShadow`+shadow-frustum config fields), `shadow.hpp` (depth texture/format helpers, hardware comparison sampler via `enable_compare`/`compare_op` — first use of that SDL_GPU feature in this codebase, depth-only shader+pipeline). Verified via a real depth-render + downloaded-pixel check against a hand-computed ortho-depth value.

**M8 done**: real directional+spot shadow sampling wired into `shader_chunks::SHADOW_REAL_FUNC` (3×3 PCF via `sampler2DShadow`), `ShaderBuilder::Shadow(int)` is no longer inert (kept the original int-parameter fluent API — `.Shadow(4)` — for compatibility with the user's originally-requested syntax, but now interprets it as a simple on/off since PCF kernel size isn't independently configurable). Shadow-casting spot lights capped at 2 (`MAX_SPOT_SHADOWS`, matches the existing bounded-light-count philosophy). `PipelineKey` gained `hasShadows: bool` (single flag, not a complex per-type breakdown — deliberately simpler than the original plan sketch: shadow *variant selection* happens per-draw via runtime uniforms `uDirShadowEnabled`/`uNumSpotShadows`, not separate shader permutations per light-type combination). `Canvas::End()` now does shadow depth pre-passes (one per shadow-casting light) before the main color pass, reusing the same `m_drawList`. Verified end-to-end with a real two-pass (caster→shadow map→shaded receiver) pixel-exact test: occluded pixel reads exactly 0, unoccluded reads 255.

**M9 done**: point-light cubemap shadows. Deliberately used a **color cubemap storing linear distance** (R32_FLOAT, `CreatePointShadowCubeTexture`/`BuildPointShadowCasterShaderProgram` in `shadow.hpp`), not a depth cubemap with hardware compare — matches three.js's own technique and sidesteps depth-cubemap sampling, which has zero precedent in this codebase or wrapper. `ComputePointShadowFactor` does the distance compare manually in GLSL (`texture(uPointShadowMap, -toLight).r` vs the fragment's actual distance, ±`uPointShadowBias`). Capped at 1 shadow-casting point light (first one found with `castShadow=true`), rendered via 6 passes into `layer_or_depth_plane=0..5` of the cube texture using `PointLight::ShadowViewProjection(faceIndex)` (already built in M7). The face-index-to-`samplerCube`-direction mapping (SDL_GPU's `layer_or_depth_plane` ordering vs GLSL's standard +X,-X,+Y,-Y,+Z,-Z major-axis convention) was **never previously exercised** and worked correctly on the first real test run — confirmed empirically, not just assumed. Point-shadow fields folded into the same `LightUBOWithShadow`/`LIGHT_UBO_SHADOW` (still binding=1, still within the 4-UBO cap) rather than the light's own position (redundant with the existing `PointLightUBO` array entry — the shader looks up `uPointLights[uPointShadowLightIndex].position` instead of duplicating it). New sampler slot: fragment `set=2 binding=4` (`samplerCube`, plain — no `enable_compare`, unlike the 2D shadow maps). Verified with the same darkened-vs-lit pixel-contrast technique as M8 (occluded=0, lit=255).

**M10 done**: hand-rolled Radiance RGBE (.hdr) decoder (`hdr_loader.hpp`, `LoadHdrEquirectangular`) — flat and new-style-RLE (4-channel-plane, dump+run) scanlines both supported; old-style RLE and non-standard orientations explicitly not supported (documented restriction, covers the vast majority of real files). Verified against a synthetic in-memory-generated `.hdr` file exercising both encodings, no real asset needed.

**M11 done**: equirect→cubemap conversion + skybox, in two new files: `cubemap.hpp` (generic reusable cube-face-capture infra — `CubeFaceViewProjection`, `CubeVertices()` unit cube, `CreateCubeCapturePipeline` — deliberately generic so M12/M13's irradiance/prefilter passes reuse the same pipeline-creation helper with a different fragment shader) and `environment.hpp` (`Environment{cubemap}` + `LoadEnvironmentFromHdr`, ties HDR loading + upload + 6-face conversion render together, called once at load time). `Canvas::SetEnvironment(const Environment&)` stores a non-owning `Ref` (same ownership contract as `Material::albedo` — caller keeps the `Environment` alive). Skybox is drawn first in the main color pass with depth test/write both off (subsequent real geometry naturally overdraws it — no depth-trick needed), using a translation-stripped camera view (`LookAt({0,0,0}, target-position, up)`). Verified with a synthetic **periodic** (not discrete-block) longitude color gradient — chosen specifically because a discrete-block pattern would place a hard edge exactly on the -X direction's equirect seam (u=0/1), which is exactly where one of the natural test directions lands; a periodic function sidesteps that alignment problem entirely regardless of exact texel/filtering alignment. All 4 equatorial faces (+X/-X/+Z/-Z) matched expected colors on the first real run; pole faces (+Y/-Y) intentionally not asserted (equirect mapping is singular there).

**M13 done**: specular prefiltering (`cubemap.hpp::BuildPrefilterShaderProgram`, GGX importance sampling, Karis/Epic split-sum, standard Hammersley/RadicalInverseVdC low-discrepancy sequence) — one pass per (mip level × face), `PREFILTER_MIP_LEVELS=5`, roughness = mip/(levels-1), rendered into `GpuColorTargetInfo.mip_level` (first use of that field in this codebase). BRDF LUT is architecturally distinct — new file `brdf_lut.hpp` — a 2D full-screen quad render (no view-projection needed at all, straight NDC passthrough), analytic `IntegrateBRDF(NdotV, roughness)` outputting `(scale, bias)` to an RG float texture. **Note**: the IBL-specific geometry-term `k=roughness²/2` (Karis) is a *different* formula from the direct-lighting `k=(roughness+1)²/8` already in `shader_chunks.hpp` — real risk of accidentally merging/reusing the wrong one, kept deliberately separate and documented. Verified via qualitative corner checks (any LUT corner should show near-mirror behavior at least once, near-grazing Fresnel behavior at least once) — not exact values, matching the plan's own stated bar for this milestone.

**M14 done**: IBL wired into the real PBR shader. Key discovery: adding IBL would have needed a 5th fragment UBO slot (an "IBL enable" flag) but the 4-slot cap was already maxed out (see M8's constraint) — solved by **repurposing `MaterialUBO`'s existing unused `padding0` field as `uUseIBL`** (renamed, zero new uniform buffers needed; IBL only needs new *samplers*, which had headroom). New `IBL_ENABLED` `#ifdef` guard in `ShadeSurface` (`shader_chunks.hpp`), mirroring the `SHADOW_ENABLED` pattern from M8. Binding numbers for the 3 new samplers (irradiance/prefiltered cubemaps + 2D LUT) depend on whether shadows are *also* active in that pipeline permutation — solved with two chunk variants (`SAMPLER_IBL_NO_SHADOWS` at bindings 1-3, `SAMPLER_IBL_WITH_SHADOWS` at bindings 5-7) selected by `ShaderBuilder` at generation time, and `Canvas::End()`'s sampler-binding array is now built dynamically (`std::array<...,8>` + running `count`) to cover all 4 combinations of `{hasShadows, hasEnvironment}`. `PipelineKey` gained `hasEnvironment: bool`; `Canvas::SetEnvironment` stores 4 non-owning `Ref`s (cubemap/irradiance/prefiltered/brdfLut) matching `Material::albedo`'s ownership contract. Verified via a genuinely useful integration test: a uniform-color synthetic environment makes irradiance/prefiltered trivially ≈ the source color (per M12/M13's own math), so the test reads the **actual baked BRDF LUT value** at test time and asserts the final shaded pixel matches `L*(kD + F0*scale + bias)` — this isolates "does `ShadeSurface` correctly apply the split-sum combination" from "is the LUT/irradiance/prefilter precomputation itself correct" (already covered separately in M12/M13), and passed on the first real run.

**M15 done**: `Points`/`LineSegments` (`point_line.hpp`) — new `PrimitiveTopology{TRIANGLES,LINES,POINTS}` enum, threaded through `PipelineKey`/`DrawCall`/`Canvas::DrawMesh(...)`'s new optional param into `info.primitive_type` (previously hardcoded to `TRIANGLE_LIST`). `Mesh::FromPoints`/`FromLineSegments` build identity-indexed vertex buffers (`Mesh` always requires non-empty indices even though point clouds have no real use for them). Both subclasses override `Shape::OnDraw` directly rather than using its per-group logic. Verified end-to-end.

**M16 done**: `Sprite` (`sprite.hpp`) + `InstancedMesh` (`instanced_mesh.hpp`). Sprite's billboard math is a real, non-obvious bug worth remembering: the standard "two `FromTo()` compositions" technique (align forward, then twist-correct up) **only works if the up vector used in the twist step is already perpendicular to the now-aligned forward axis** — using the raw `camera.up` field directly is wrong whenever the camera isn't looking exactly along a direction perpendicular to its own up (i.e. almost always), because `camera.up` is just a reference vector, not the camera's true orthogonalized up. Fix: Gram-Schmidt orthogonalize it first (`right = up×toCamera`, `orthogonalUp = toCamera×right`) before the twist `FromTo`. Caught by a real CPU-only test that failed on the first attempt with realistic (non-axis-aligned) camera coordinates — worth remembering to always test billboard/look-rotation math with a camera position that ISN'T conveniently axis-aligned. `InstancedMesh` needed a second vertex buffer (slot 1, `input_rate=INSTANCE`, mat4 spread across locations 4-7 as 4 vec4 columns — standard GLSL rule for a `mat4` vertex input) and a new `PipelineKey.instanced` flag (vertex layout itself differs, not just shader defines). Deliberately does **not** support shadows or IBL this round (scope cut — would need per-instance shadow rendering, a much larger undertaking); the instance matrix fully replaces `uModel` including the normal-matrix approximation (upper-3×3 of the instance matrix, matching three.js `InstancedMesh`'s own default simplification for non-uniform scale). Both verified via real pixel-readback (not just `GetError()` checks) confirming genuinely separate instances render at separate screen positions.

**M17 done**: `SkinnedMesh`/`Bone` (`skinned_mesh.hpp`, `skinned_geometry.hpp`). `Bone` is literally just `class Bone : public Object3D {};` — `Object3D` already has everything a joint needs (transform + hierarchy + `WorldMatrix()`), so this exists purely to name intent at call sites, not to add behavior. Real architectural finding: `SkinnedVertex3D` needed a **parallel GPU-buffer-owning type to `Mesh`** (`SkinnedGeometry`, in a new file included *before* `canvas.hpp`, mirroring how `Mesh` itself precedes it) rather than templating `Mesh<VertexT>`, since `Mesh`'s `EnsureGpuBuffers` is hardcoded to `Vertex3D` throughout — deliberate duplication over premature genericization, consistent with the project's stated style. Bone matrices (`bone.WorldMatrix() * inverseBindMatrix`, inverse bind captured once at construction) go into a `GRAPHICS_STORAGE_READ` **storage buffer** (not a UBO — `MAX_UNIFORM_BUFFERS_PER_STAGE=4` is already maxed out, and a UBO would also cap bone count) — this was the exact risk flagged in the plan (`BindVertexStorageBuffers` "needs confirming"), and turned out to already exist and work fine on the first try (`gpu.hpp:541`, first real use of it in this codebase). `ShaderCompiler::CompileShader` gained an optional `numStorageBuffers` parameter (default 0, backward compatible) since `SDL_GPUShaderCreateInfo.num_storage_buffers` is a field distinct from `num_samplers`/`num_uniform_buffers` that nothing previously set. Explicit scope cut (per the plan): no keyframe `AnimationClip`/`AnimationMixer` — only manual bone posing via the inherited `Object3D::SetRotation()` etc., verified with a real 2-bone-chain pixel-readback test (rotate the child bone 180°, confirm only the bone-weighted half of the mesh visibly moves) that passed on the first real run.

**M18 done**: `LOD` (`lod.hpp`) — the simplest of the M15-M18 batch, exactly as scoped in the plan: `OnDraw()` doesn't draw anything itself, it just toggles `SetVisible()` on its levels (owned via the normal `Object3D::Add()`) before `Object3D::Traverse()` recurses into children — since `Traverse()` already skips invisible subtrees, this needed **zero** `Canvas`/pipeline changes. Distance-only level selection (camera position to node's world-space translation), no bounding-sphere/frustum culling, matching three.js's own `LOD` default. Verified via a real (if not fully hermetic — still needs a live GPU device to construct a `Canvas`, since `LOD::OnDraw` reads `canvas.GetCamera()`) CPU-side test across 4 camera distances including an exact-threshold boundary case.

**M19 done**: final combined example + regression pass. No real-world `.hdr` file existed anywhere in the repo or environment (only an LDR `.jpg` equirect, unusable by the Radiance-only loader, and no internet access) — generated one procedurally instead: `/tmp/gen_hdr_sky.py` (a throwaway script, not committed) hand-encodes RGBE via `math.frexp` matching the C++ decoder's exact `scale = 2^(e-136)` math, producing a 256×128 flat-encoded sky gradient (blue zenith → orange horizon → dark ground, plus a Gaussian sun disc) committed as a real asset at `assets/textures/equirectangularmaps/procedural_sky.hdr`. Added a permanent regression test (`HdrLoaderSmokeTest::LoadsRealAssetUsedByShowcaseExample`) loading this actual file (not just an in-test synthetic one) to catch future drift between the loader and the asset. New example `examples/render3d_shadows_ibl_showcase.cpp` combines every M7-M18 deliverable in one scene: `LoadEnvironmentFromHdr` (skybox + full IBL split-sum on 2 PBR objects), a directional+spot+point light all with `castShadow=true` (a cube and sphere cast real shadows onto a ground plane), and one of each remaining `Object3D` subclass (`Points` particle ring, `LineSegments` ground-plane axes, a billboard `Sprite`, a `4×3` `InstancedMesh` grid, a hand-posed 2-`Bone` `SkinnedMesh` animated every frame via `SetRotation()` — no keyframe clips, per the M17 scope cut — and a 3-level `LOD` sphere placed to land in its middle tier at the fixed camera distance). Note the M16 scope cut means the instanced grid and skinned arm do **not** cast/receive shadows or IBL — only the plain `Shape` objects (cube, sphere, ground) do, since `Canvas::End()`'s shadow pre-pass only iterates `m_drawList`, not `m_instancedDrawList`/`m_skinnedDrawList`. Verified by real compile + real run under ASan/UBSan for several seconds with zero stderr output (no GPU validation layer available to enable in this `Canvas::Create` — it doesn't pass `debugMode=true` — so a clean multi-second run with sanitizers active is the strongest available signal here; per-subsystem pixel-exact/closed-form correctness was already established individually in M7-M18's own tests). `make lint` scoped to the two new/touched files (the example + the extended `hdr_loader_smoke_test.cpp`) found zero warnings anchored in them or in any render3d header; the only findings were a pre-existing `clang-diagnostic-infinite-recursion` false-positive in `sdl3/stdinc.hpp` (confirmed present even when linting the untouched Phase-2 `render3d_showcase.cpp`, so unrelated to this work) plus pre-existing naming warnings in `sdl3/time.hpp`/`ttf.hpp`/`vulkan.hpp` (also untouched). Full regression: all 8 render3d-relevant binaries green, 48 tests total, zero regressions.

**Debugging note**: `environment_smoke_test.cpp` initially included `render3d/environment.hpp` *before* `sdl3/sdl3.hpp`, unlike every other test file in this repo (which include the SDL umbrella first) — this compiled fine until `brdf_lut.hpp` was added to the include graph, at which point it broke `sdl3/render.hpp` (missing `Point`/`Color`/`Rect` types, order-dependent). Fixed by swapping the include order to match the established convention. **Lesson: always put `#include "sdl3/sdl3.hpp"` before any `render3d/*.hpp` include in test files** — the render3d headers pull in `sdl3/gpu.hpp` directly (not the full umbrella), and their transitive include order is not guaranteed safe standalone.
