Phase 8 (see [[project-ecs-render3d-bridge]] for Phase 7) started at the plan's originally negotiated scope (a plain in-process table store, explicitly NOT a SQL engine) but was deliberately reopened and expanded mid-phase by direct user request, twice, pointing at a specific reference project: https://github.com/czLad/cs8_finalProject_SQL_Database (a student DBMS: tokenizer → parser → shunting-yard/RPN → B+Tree index → binary file storage). An `AskUserQuestion` was asked first to confirm this was a deliberate scope reopening rather than the loose inspiration the plan doc originally anticipated — the user's first answer was "keep original scope," immediately followed by an explicit, detailed follow-up message asking for "un vrai parser sql et un factory builder... comme avec ce projet," which was treated as the authoritative final instruction. **The plan document's own Phase 8 section is now stale/incomplete for this phase** — this memory doc is the record of what was actually built.

Built in 3 sequential, independently-verified dispatches (each reviewed at the code level, not just by trusting green tests — every file was read in full, the B+Tree's insert-split and delete-rebalance invariants were hand-traced, the shunting-yard's NOT/AND precedence interaction was hand-traced through a worked example):

## Layer 1 — original scope: `table.hpp` / `query.hpp` / `storage.hpp`

`sql::Table<Row>` — stable-id-under-deletion row store (mirrors `ecs::EntityAllocator`'s pattern, simpler: tombstone-forever, no generation reuse), persistence-agnostic. `query.hpp` — small predicate combinators. `storage.hpp` half 1: `SaveProjectJson`/`LoadProjectJson` (generic `data::Node` tree ↔ JSON file). Half 2: `SaveTableCsv`/`LoadTableCsv` via `data::CsvDocument` — critical constraint documented and correctly handled: CSV's `data::Node` root is COLUMNAR (Object of column-name → Array-of-cells), not row-shaped, easy to get backwards. `tests/sql_smoke_test.cpp`, 5/5.

## Layer 2 — real SQL parser + factory/builder

- `token.hpp` — hand-written lexer (keywords, identifiers, string/int/float literals with `''`-escaping, operators, punctuation).
- `expression.hpp` — genuine shunting-yard → RPN for WHERE-clause expressions (comparison ops tightest, then `NOT`, then `AND`, then `OR`; parens override), plus a left-to-right stack evaluator. `Compare3Way` does numeric INT/FLOAT cross-comparison, STRING lexicographic, BOOL ordering; type mismatches are a clear `Err`, never silent `false`. Deliberately does NOT port the reference project's hand-rolled stack/queue/linked-list/sort — this codebase uses `std::vector`/`std::unordered_map` throughout, porting those would have been pure regression.
- `schema.hpp`/`statement.hpp`/`parser.hpp` — `Schema`/`ColumnDef` (4 scalar types only), a `std::variant` statement AST, recursive-descent `ParseStatement` supporting `CREATE TABLE`/`INSERT INTO`/`SELECT [WHERE]`/`DELETE [WHERE]`/`DROP TABLE`, every error path naming what was expected vs. found.
- `database.hpp` — `Database` (the "factory": named-table registry), reusing `Table<std::vector<data::NodePtr>>` from layer 1 with zero changes to it. `ExecuteDelete` collects matching ids in a read-only pass before deleting (avoids mutate-while-iterating, the same discipline established repeatedly across this session's ECS-adjacent work).
- `query_builder.hpp` — `QueryBuilder`, the fluent C++ "builder" half of "factory builder": builds RPN directly from `.Where(col,op,val)` calls (flat AND-chain, no shunting-yard needed since there's no precedence ambiguity to resolve), executes via `Database::ExecuteSelectStatement` — reuses the exact same WHERE-evaluation path as text-based `Execute`, never duplicated.
- `tests/sql_parser_smoke_test.cpp`, 13/13, real end-to-end pipelines with exact-value assertions (not just row counts) — including a hand-traced-correct `WHERE id > 1 AND active = true` precedence test and a `QueryBuilder`-vs-hand-written-SQL cross-check.

## Layer 3 — binary storage + B+Tree index

- **`database.hpp` refactor** (behavior-preserving, re-verified via `sql_parser_smoke_test` immediately after): `CreateTable`/`InsertRow` extracted as public methods taking already-typed `Schema`/`Row` data directly; `ExecuteCreateTable`/`ExecuteInsert` become one-line forwarders. This exists so binary loading never needs to round-trip through generated SQL text (a STRING cell containing a literal `'` would need re-escaping to survive that — needless risk for structured data that was never user-typed SQL).
- `binary_storage.hpp` — a custom binary format (magic `"SQLB"` + version, per-table name/schema/type-tagged rows, little-endian multi-byte values, length-prefixed strings) built into an in-memory byte buffer with bounds-checked pack/unpack helpers (`Err` on any truncated/corrupt read, never an out-of-bounds read). `SaveDatabaseBinary` walks `Database`'s existing public API (`TableNames`/`GetSchema`/`Execute("SELECT * FROM ...")`) — no new raw-iteration surface needed. `LoadDatabaseBinary` reconstructs via `CreateTable`/`InsertRow` directly.
- `btree_index.hpp` — `BTreeIndex`, a real in-memory B+Tree (configurable minimum degree `t`), keyed by a scalar `data::NodePtr` via `expression.hpp`'s `Compare3Way` (reused, not re-derived). Duplicate keys allowed (each leaf entry maps one key to a row-id list). **Insert**: standard split-on-reaching-`2t-1`-keys, median promoted (copied for leaf splits, since leaf data must stay in leaves; moved for internal splits). **Remove**: a real, complete deletion — borrow-from-sibling (preferring left) or merge-with-sibling on underflow below `t-1` keys, propagated up through parents as recursion unwinds, with correct root-collapse when a merge empties the root down to one child. This is the one piece the reference project's own README admits is incomplete ("remove operation prepared but lacking disk management for DELETE") — this implementation doesn't leave it unfinished. Verified by hand-tracing the key-count invariants through both the split and merge/borrow paths (every post-split/post-merge node size checked against `MinKeys()`/`MaxKeys()` bounds), and by a real test that forces both node splits (30-50 inserts) and rebalances (deletions past underflow), confirming the tree stays correctly queryable afterward.
- `database.hpp` — `CreateIndex`/`LookupByIndex` wire a `BTreeIndex` per `(table, column)` on top of existing `Table<Row>` storage, as an optional secondary index. **Deliberately a snapshot, not live-maintained**: rebuilt fresh each `CreateIndex` call by scanning current live rows; a row inserted afterward is invisible to `LookupByIndex` until `CreateIndex` is re-called (a false negative, the documented and accepted failure mode), while a row deleted since is transparently dropped from results (never resurrected with stale data, since `LookupByIndex` resolves every stored row id back through the live table). Chosen deliberately over full live-index maintenance: correctness-over-completeness, an honestly-scoped snapshot beats a live-synced index with an untested interleaved-mutation edge case.
- `tests/btree_index_smoke_test.cpp` (7/7, isolated — no `Database` dependency) and `tests/sql_binary_storage_smoke_test.cpp` (6/6, including a STRING value containing a literal `'` round-tripping byte-for-byte through the binary format, and a test proving the snapshot staleness caveat is actually true).
