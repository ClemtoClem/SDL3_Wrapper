M22 (Phase 3 of the engine-expansion plan — see [[project-ui-gpu-backend]] for M20, [[project-render3d-offscreen]] for M21) is the first real consumer of M21's offscreen-compositing primitive: `ui::Viewport3D`, a widget that renders an independent `render3d::` scene into a screen region without the widget's own box dimensions distorting the 3D projection, and supports multiple independent scenes/cameras in one UI for free.

## M22 done — `lib/include/ui/viewport3d.hpp`

- **`UiViewport3D` component**: `render3d::Object3D *root` — a **non-owning** pointer, deliberately, since `Object3D` is non-copyable/non-movable (a move would invalidate the `parent` pointers its existing children hold) — the caller owns the scene root (same pattern as `root.Add(...)` in `examples/render3d_showcase.cpp`), the widget just references it. Owns its own `render3d::Camera` (plain value struct) and its own `render3d::OffscreenTarget` (M21) — **zero GPU state shared between two `Viewport3D` widgets**, so multiple independent scenes/cameras falls out for free from the ownership model, not from any special-casing.
- **`Viewport3DSystem::Update(world, canvas, ren)`**: the `NodeGraphSystem` precedent (dedicated system, not folded into generic `LayoutSystem`/`InputSystem`) applied to a new widget kind. Collect-then-mutate via `world.EntitiesWith<UiViewport3D>()` (copies first) before touching any component — the established defense against this codebase's real, previously-hit ECS iterator-invalidation hazard (`StyleSystem::Resolve` was bitten by this twice per `memory/project_ui_ecs_module.md`). Per viewport, per frame: read `UiComputed::screen` (post-layout resolved pixel rect — can change any frame, e.g. window resize), `OffscreenTarget::EnsureSize` to match, `RenderObjectToTexture` (M21) into a CPU pixel buffer kept as a per-widget member (avoids a per-frame realloc), then create/update an `sdl3::Texture` for display — `Texture::Create` only when the pixel size actually changed (SDL textures can't be resized in place), `Texture::Update` otherwise. Every failure point degrades gracefully (skip that widget/frame, keep last-good texture) rather than propagating an error — matches `EnsureShadowResources`/`EnsureIblSamplers`'s established philosophy.
- **Pixel format**: `R8G8B8A8_UNORM` (GPU side) confirmed byte-identical to `SDL_PIXELFORMAT_RGBA8888` (`sdl3::Texture`'s default) — no conversion needed between `RenderObjectToTexture`'s output and `Texture::Update`'s input, verified against `offscreen_smoke_test.cpp`'s own existing round-trip check rather than assumed.
- **Draw side** (`systems.hpp`, new case in `RenderSystem::DrawWidget`, same shape as the existing `UiImage` case): `DrawImageFit(ren, *displayTexture, computed.screen, ImageFit::FILL)` — `FILL` (not `CONTAIN`/`COVER`) is correct and non-distorting here specifically because `camera.aspect` was already matched to the `OffscreenTarget`'s exact pixel dimensions inside `RenderObjectToTexture` (M21) — the texture itself is never a mismatched aspect ratio needing letterboxing, `FILL` just positions it exactly over the widget rect.
- **`UiFactory::Viewport3D(render3d::Object3D &root, render3d::Camera camera = {})`** — standard `WidgetBuilder` pattern (one `Option<UiViewport3D>` field, one `Spawn()` line), no surprises.
- **`ui::Ui`**: `Initialize(render3d::Canvas&)` (a stub since M20) is now real — `Ui` owns a `Viewport3DSystem` member, and `Render()`/`Draw()` calls `viewport3d.Update(...)` (only when a `Canvas` was registered — no-op, zero overhead otherwise) in the correct position: **after** `layout.RunIfNeeded` (needs `UiComputed::screen` already resolved) but **before** `render.Run` (the 2D draw pass needs each `displayTexture` already fresh to blit it the same frame).

## The open architectural question from M21's research, resolved empirically

M21's own writeup flagged as uncertain whether `sdl3::Renderer` (SDL_Renderer) and `render3d::Canvas`/`GpuDevice` (SDL_GPU) could coexist claiming the **same window** simultaneously. **Confirmed empirically in `examples/ui_viewport3d_demo.cpp`: yes, they can** — `sdl3::Renderer::Create(window)` and `render3d::Canvas::Create(window, w, h)` both succeed on the same window, and the combined app runs clean under ASan/UBSan for several seconds. The load-bearing constraint (which the example respects, and any future `Viewport3D` consumer must too): **never call `Canvas::Begin()`/`End()` or present anything through the `Canvas` itself** on that shared window — only use it via `RenderObjectToTexture`'s internal, separate, non-swapchain command buffers (exactly what `Viewport3DSystem::Update` already does). Only the `sdl3::Renderer` ever actually presents to the window in this model; the `Canvas`/`GpuDevice` is used purely as an offscreen rendering engine. This resolves the coexistence question for M23 (widget shader effects, same underlying primitive) and M30+ (the level editor) too — no further investigation needed there.

## Scope cuts (deliberate, inherited from M21, not relitigated here)

No shadows/IBL inside a `Viewport3D`'s rendered scene (M21's own cut). No interaction with the 3D content (camera orbit, click-to-select) — purely a display widget this milestone; interaction is the level editor's concern (M30+).

## Verification

New `tests/viewport3d_smoke_test.cpp`, 3 tests, all passing (real GPU compile + run): `NoStretchAtDifferentAspectRatiosThroughFullPipeline` (two widgets at different pixel sizes, silhouette/edge-pixel checks against hand-computed projections confirm neither is stretched), `DistinctCamerasOnSameSceneShowDifferentContent` (two widgets, same scene, different cameras, confirmed genuinely different rendered pixels), `UpdateSafeWithMultipleViewportsAndUnrelatedEcsChurn` (multiple viewport entities plus unrelated ECS mutations the same frame — confirms the collect-then-mutate defense actually holds). New `examples/ui_viewport3d_demo.cpp` (two very-different-aspect-ratio panels, same scene, two cameras, embedded in an otherwise normal 2D `ui::` app) built and ran clean under ASan/UBSan. Full regression: `render3d_smoke_test` (25/25), `offscreen_smoke_test` (3/3), and 3 `ui_smoke_test_*` binaries (`_1`, `_3`, `_8`) all still pass — confirms `ui::Ui`'s frame-lifecycle change doesn't regress apps that never call `Initialize(Canvas&)`. Scoped clang-tidy on `viewport3d.hpp`: zero warnings anchored in the file (only the pre-existing, already-documented `stdinc.hpp` false-positive, unrelated).
