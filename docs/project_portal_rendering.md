M30 (Phase 9's first sub-milestone — see the plan for M31/M32, editor UI and play mode, still pending) ports the portal-rendering technique from the reference project `/home/clement/Documents/Programs/Programs_C/SDL/Games_Projects/NonEuclidean` — algorithm-only, zero code reuse (separate raw-OpenGL/GLEW stack).

## The single highest-risk piece in the whole 9-phase plan — and a real bug caught before it shipped

`Camera::ClipObliqueNearPlane` (Lengyel's oblique-near-plane-clipping technique) was NOT a safe literal port. The reference project's matrix is OpenGL-convention (row-major-ish storage, Z ∈ [-1,1]); this codebase's `math::FMatrix4` is column-major (`m[col*4+row]`, GLSL convention) and targets **Vulkan clip space (Z ∈ [0,1])** — confirmed via `FMatrix4`'s own doc comment and empirically via `Perspective()`'s "near→0, far→1" behavior.

I derived and numerically verified the formula myself (a standalone scratch C++ program against the real `math::FMatrix4`/`Camera`, not just paper derivation) before writing any real code, and found: the reference's `newRow2 = c - row3` subtraction specifically retargets the near plane to OpenGL's z_ndc = -1. Ported literally (even with correct row/column index translation via `At(r,c)`), points on the specified clip plane landed at z_ndc = -1, NOT this codebase's near value of 0 — a whole extra buffer zone of valid geometry between z_ndc=-1 and z_ndc=0 would have been silently clipped away by Vulkan's stricter `z_ndc ∈ [0,1]` hardware test. The fix: drop the `- row3` term entirely (`newRow2 = k*cPlane` directly), which makes z_clip = 0 exactly on the plane for any k — matching Vulkan's near=0 target directly — with `k` solved from the far-corner-preservation constraint (`k = w_clip(q)/cPlane·q`, `q` = the original projection's inverse applied to the sign-selected clip-space corner). Verified via a real numeric test program checking plane points land at z_ndc≈0 to float precision, far plane preserved at z_ndc≈1, and this holds for both axis-aligned and oblique planes and both a trivial and an arbitrarily translated+rotated camera. This is now `tests/portal_smoke_test.cpp` (5 tests) permanently.

## What was built

- `lib/include/render3d/camera.hpp` — `Camera::ClipObliqueNearPlane` (above), later refactored into a shared `detail::ClipObliqueRow` free function so `portal.hpp` can apply the same verified math against an explicit (non-`this`) view matrix.
- `lib/include/render3d/offscreen.hpp`/`canvas.hpp` — new `Canvas::RenderObjectOffscreen`/`RenderObjectToTexture` overloads taking an explicit view-projection matrix directly, instead of always deriving it from a `Camera` internally (extract-and-forward refactor, existing 3-arg overloads become one-line forwarders — behavior-preserving, re-verified via the full `render3d_smoke_test` suite). Needed because portal rendering must inject an oblique-clipped projection the plain `Camera` struct can't express through its own fov/aspect/near/far fields.
- `lib/include/render3d/portal.hpp` — `Portal` (non-owning `node`/`linkedPortal`, `delta`/`deltaInv` recomputed fresh every call from both portals' current `WorldMatrix()` — never cached, matching this codebase's established convention) and `RenderPortalRecursive` (recursion up to `maxDepth`, bounds-checked via `FFrustum::Intersects`, composites by setting the linked portal's `Shape::Material::albedo` to the just-rendered offscreen color texture — zero additional compositing code needed, the normal draw path does the rest).

  **A second real bug the dispatched agent caught and fixed, verified empirically, not just on paper**: the reference project's shipped virtual-camera composition is `worldView *= portal.delta`. Applied literally against THIS codebase's `Portal::delta` definition (`delta = worldB * worldA⁻¹`), that is backwards — it doesn't send the virtual camera's own position to the view-space origin. The correct composition, re-derived and confirmed both by a concrete numeric check and by a recursive round-trip identity (enter A then B returns to the start, since `B.deltaInv == A.delta`), is `virtualView = baseCam.ViewMatrix() * portal.deltaInv`. I independently re-verified this via matrix-inverse algebra (`Wv = delta·Wr ⟹ Wv⁻¹ = Wr⁻¹·delta⁻¹`) and it matches. The reference's own `delta` is presumably defined with the opposite multiplication order — the underlying technique transfers, the literal formula does not.

- `lib/include/physics/portal_teleport.hpp` — `PortalPlane` (a render3d-independent mirror of one portal's plane + delta matrices — preserves `physics::`'s existing zero-dependency-on-render3d boundary, per [[project-physics-module]]) + `TeleportBodiesThroughPortals`: a segment-bounded (not just infinite-line) front-to-back crossing test via `FPlane`/`FRay`, applying `delta` uniformly to position/orientation/linear+angular velocity. Orientation transform needed a real rotation-matrix→quaternion conversion (Shepperd's method, numerically stable near 180° rotations) that didn't already exist in `math::` (`FQuaternion::ToMat4()` only goes the other direction) — derived and cross-checked term-by-term against this codebase's own matrix layout, verified by a round-trip test.
- `lib/include/render3d/picking.hpp` — `PickMeshFace`: raycast-vs-mesh-face picker respecting `Mesh::Group` boundaries, reusing the existing Möller–Trumbore `FRay::Intersects`. Transforms the ray into local space (cheaper than transforming every vertex) but correctly recomputes `t`/hit-point in world space afterward — necessary, not cosmetic, since a scaled `worldMatrix` means a raw local-space `t` would be in the wrong units.
